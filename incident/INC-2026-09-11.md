## What happened

Overnight support picked up a complaint from a user on account ending **4821.

> "Your app says I spent ₹92,213.10 on a water can. I paid ₹5. Fix this, I am
> not able to trust anything else on this screen now."

The Track screen does show a debit of **₹92,213.10** against merchant
**UPI/WATER CAN**. The user is right: the bank SMS behind it says ₹5.

## Resolution

### 1. Reproduced

`src/test/java/in/simplifymoney/ledgersync/IncidentINC20260911Test.java` feeds
the exact SMS from `incident/app.log` (`msg=m-00004-9c11ae`) through
`Parsers.parse()` end to end. Before the fix below it returns a `ParsedTxn`
with `amount=92213.10`; after, `amount=5.00`. `AmountsTest` pins the same
behaviour one layer down, directly against `Amounts.first()`.

### 2. Cause

`src/main/java/in/simplifymoney/ledgersync/parse/Amounts.java`, line 17-18,
the `AMOUNT` pattern:

```java
Pattern.compile("(?:Rs\\.?|INR)\\s*([0-9,]+\\.[0-9]{2})");
```

The decimal part (`\.[0-9]{2}`) was **required**, not optional. "Rs.5" has no
paise, so it never matched; `first()` kept scanning and matched the next
`Rs./INR` figure in the message instead - in this SMS shape that is always
`Avl Bal:`. The parser never saw an error: it got a number back and saved it.

### 3. Blast radius

**40 of the 522 messages** in `fixtures/corpus-a.jsonl` are affected - **26
distinct real transactions** (some affected messages are the same underlying
SMS uploaded twice; both copies carry the bug). Of the 40: 38 were saved
with the wrong amount (almost always the account's available balance, since
that is the next `Rs./INR` figure after the transaction amount in every
affected shape); 2 have no second `Rs./INR` figure anywhere in the message
(a couple of the transaction-alert emails), so `first()` returned nothing and
`IngestService` silently dropped them - a real transaction with zero rows to
show for it, which is arguably worse than a wrong number.

**The rule:** a message is affected if and only if the bank wrote the
transaction amount as a whole number of rupees - no paise, so no `.NN` suffix
("Rs.5", "Rs 20", "INR 18,000"). Any amount with paise, even `.00`, was
already fine. This cuts across every message shape and both banks - it is a
property of the amount, not of the sender or the channel.

### 4. Fix

Made the decimal suffix optional:
`(?:Rs\.?|INR)\s*([0-9,]+(?:\.[0-9]{2})?)`. `toDecimal()` already
`.setScale(2)`s the result, so a bare `"5"` correctly becomes `5.00` with no
further change needed.

Tests added, all of which fail on the pre-fix pattern and pass on the fixed
one: `AmountsTest#wholeRupeeAmountIsNotConfusedWithTheAvailableBalance` (the
exact incident SMS), `#wholeRupeeAmountWithThousandsSeparatorIsReadDirectly`,
`#wholeRupeeAmountWithNoSpaceAfterRsIsReadDirectly`, and the end-to-end
`IncidentINC20260911Test`.

### Why the existing suite stayed green

`AmountsTest` had five cases before this fix, and every single one used an
amount with a decimal fraction - `2499.50`, `333.33`, even the round
`45,000.00` was written with `.00`. Not one exercised a message where the
bank omitted the paise. The bug is invisible to "does it extract a number"
tests and only shows up when you specifically ask "what if there's no
decimal point at all" - which nobody had asked yet.

### Five lines, for the incident channel

**What broke:** `Amounts.first()` required a decimal point in the amount; a
whole-rupee debit like "Rs.5" silently matched the *next* `Rs./INR` figure in
the SMS instead - almost always the account balance.
**How we found it:** reproduced the exact SMS from `app.log` end to end
(`IncidentINC20260911Test`), then grepped `corpus-a.jsonl` for every message
where the bug's old/new regex disagree.
**Who was affected:** 26 real transactions across 40 messages on the
corpus we can check (account 4821 and others) - any transaction, on any
account, where the bank wrote a whole-rupee amount with no paise.
**Why it cannot recur:** the decimal suffix is now optional in the amount
regex, `AmountsTest` and `IncidentINC20260911Test` pin the exact incident SMS
and two more whole-rupee shapes, and both fail loudly against the old
pattern.
**Not yet done:** the 26 historical transactions already saved with the wrong
amount (including the legacy row in `V2__seed.sql`) still need a one-off
correction pass in production - this fix stops new bad rows, it does not
retroactively repair old ones.
